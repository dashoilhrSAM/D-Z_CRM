# 批量配置工作台（Bulk Setup Desk）——完整实施方案

> 起因：老板问「有没有一个界面能管理所有这些 Excel 上传下载 —— 我能挑要下载哪几部分，
> 也可以全部；上传后能看到这次的改动是什么，并且能**逐条 拒绝 / 批准 / 修改**，把录入管起来」。
>
> 这份文档回答的是**怎么做**，以及**哪些决定需要老板拍板**。

---

## 一、现在是什么样（差距在哪）

| 能力 | 现状 |
| --- | --- |
| 下载 | 能下载，但**八张表只能一次全下** —— 不能只挑几部分 |
| 上传后看改动 | 有预览：逐行 新增 / 修改 / 删除 / 无变化 / 出错，带**旧值 → 新值** |
| 逐条决定 | **没有** —— 只有「应用」一个按钮，全批或全不批 |
| 在界面里改数据 | **没有** —— 要改就得回 Excel 改、再重传 |
| 录入历史 | 只有审计日志（技术格式），没有「这次导入做了什么、谁批的、几条被拒」 |

**一句话**：现在的预览是「给你看」，不是「让你管」。

---

## 二、方案（三块）

### 第 1 块：选择性下载

- 页面上勾选要下载的 sheet（默认全选），也可选**只要模板**（只有表头 + 列对照，适合全新配置）
- 工作簿的隐藏元数据里记录：版本、分店、**包含哪些 sheet**
- 导入时**只处理文件里有的 sheet** —— 没包含的部分不是「空表」，而是「这次不涉及」

> 这条很关键：否则「我这次只想改零件」传一份只含零件的文件，
> 系统会以为套餐/车辆/客户全是空的 —— 那正是「文件里没有的行绝不删除」要防的事，
> 只是换成了更粗的版本（整张表缺席），必须显式处理。

### 第 2 块：改动审核台（核心）

上传后进入审核台，按 sheet 分组，每行显示：

- 动作标签：**新增 / 修改 / 删除 / 出错**
- 字段级改动：旧值 → 新值（一列一列列出来）
- 三个动作：**批准 / 拒绝 / 修改**
  - **修改** = 就地改那几个字段（改完可以直接批准）
  - 出错的行显示原因，**就地改对**即可批准（不用回 Excel）
- 批量：**全部批准 / 全部拒绝 / 只批准没有出错的**（按 sheet，也可以整份）
- **未变化的行默认收起**（只显示要处理的），可展开查看

**应用**：只应用**已批准**的行，一个事务，**逐行回执**（哪条成了、哪条为什么没成）。

**三条不可动摇的规则**（沿用现有）：
1. 文件里没有的行**绝不删除**（要删必须在 _action 列显式写 delete）
2. **留空＝不动**（不是清成 0）
3. **出错的行不能被批准** —— 要么改对，要么拒绝

### 第 3 块：导入会话与历史（把录入管起来）

新增一张表，记录**每一次导入**：

    BulkImportSession
      id / organisationId / branchId
      fileName / fileHash(sha256) / uploadedBy / uploadedAt
      status: DRAFT（在审）| APPLIED（已应用）| CANCELLED（已取消）
      rowSummary（解析出多少行、几条改动、几条出错）
      decisionsJson（每一条：批准 / 拒绝 / 改成了什么）
      appliedSummary（应用结果）+ appliedAt

带来的能力：

- 上传即建**草稿会话** —— 审到一半可以关掉页面，**下次回来接着审**
- **历史页**：每次导入一目了然（谁、什么时候、哪个文件、改了多少、拒了多少），可下钻看逐条
- **导出这次改了什么**（给会计/老板看的变更清单）
- 会话可以**取消**（什么都不会写）

## 三、分期与产出

| 期 | 内容 | 产出 |
| --- | --- | --- |
| **P1** | 选择性下载 | sheet 勾选 + 元数据记录覆盖范围 + 导入只处理文件里有的 sheet |
| **P2** | 改动审核台 | 逐行 批准 / 拒绝 / 修改 + 批量 + **只应用已批准** + 逐行回执 |
| **P3** | 会话与历史 | BulkImportSession 表 + 历史页 + 取消 + 导出本次改动 |
| **P4** | 收尾 | 旧 CSV 导入改造成同一套判重/归一化后退役；大文件分页/虚拟滚动；导入完成通知 |

P1 与 P2 可以一起做（都在同一页面上）；P3 需要一次数据库迁移。

## 四、需要老板拍板的 6 个决定（都给了建议）

| # | 决定 | 建议 | 理由 |
| --- | --- | --- | --- |
| 1 | 服务端要不要**复验**客户端传回的计划 | **要** | 客户端只传「值 + 批准与否」，新增/修改/删除的**分类由服务端按当前数据库重新判定** —— 一次被篡改的请求不该能凭空删东西 |
| 2 | 预览之后、应用之前，**别人手改了同一条**怎么办 | **逐行拒绝并说明** | 提示「这条在预览之后被改动过，请重新导出」，而不是盲目覆盖掉别人的修改 |
| 3 | 决定保存在哪 | **存服务器（会话表）** | 关掉页面不丢、可分次审、有据可查；只存浏览器则一关就没了 |
| 4 | 「未变化」的行要不要也批准 | **不要** | 没变化本来就不写，列出来只是噪声 |
| 5 | 应用仍然**整份一个事务**吗 | **是**（只覆盖已批准的行） | 任一已批准行失败就整份回滚 —— 避免「改了一半」，那是最难收拾的状态 |
| 6 | 谁能审 | **OWNER + MANAGER（本店）**；删除仍只有 OWNER | 与现有删除门槛一致 |

## 五、明确不做（避免以后重新争论）

- **不用 Excel 管员工与角色** —— 身份与权限有红线，专用界面里有校验（见 P3 那期的文档）
- **不做自动合并客户** —— 邮箱撞车只报错，不猜（见客户表那期的决定）
- **历史单据不受影响** —— 导入不会碰到已完工的工单/发票/库存流水；有历史引用的对象只停用不删除
- **不做自由格式的 SQL / JSON 导入** —— 列定义与取值域必须由代码说了算

## 六、验收方式（沿用这一段的做法）

每一期落地后**在生产用真实数据**跑一遍，而不是只看测试：

- **P1**：只勾 3 张表下载 → 传回 → 确认**只处理这 3 张**、其余原样不动
- **P2**：故意改一条 + 留空一格 + 造一条错的 → 逐条 批准/拒绝/修改 → 应用后回数据库核对
- **P3**：审到一半关掉页面 → 回来继续 → 历史页能看到这次导入与每一条的决定
