## 改动

### 1. P5 第一刀：侧边栏品牌区显示**店名**，不再显示「分行 · 城市」

`src/app/workshop/layout.tsx` 原来读 `session.branchId` 对应的分行、拼成 `${name} · ${city}`。
现在直接读**租户名**（`Organisation.name`），prop 也从 `branchLabel` 改名 **`brandLabel`** ——
名字得说真话，否则下一个人还会往里塞分行。

为什么现在换：多租户下「分行」已经不是用户能理解的概念（`Branch` 降级为隐藏的 1:1 门店记录），
而**店名才是这家店的身份**；将来一个账号属于多家店时，这一行必须让人立刻分辨「我在哪家店」。

**P5 侦察结论（省下不少工）**：
- **分行管理 UI 已经不存在**（`src/app/workshop/settings/` 只剩 `audit-logs` / `developer` / `page`）——
  施工单里「移除分行管理 UI」这条其实已经完成了；
- `src/lib/branch-info.ts` 现在**只被 `seed-core.ts` 用**（侧边栏早就不用它了）——
  「硬编码主店身份」的隐患只剩演示数据，不再影响运行时；
- 真正剩下的大件是 **`branch-scope.ts` 的隔离职责退役**：`scopedBranchId` / `applyBranchScope` /
  `isOrgLevelRole` 仍有 **90 处**调用，而且它参与**数据分区** —— 这是 P5 里最需要小心的部分，
  不适合和别的改动混在一起做（下一步单独一片）。

### 2. 修掉反复咬人的 e2e 考勤漂移（「看起来像功能坏了」）

**现象**：`e2e/attendance-review.spec.ts` 间歇红两条（`待处置` 期望 1 实际 2），
而且**只在连跑第二次之后**出现 —— 恢复办法一直是 `prisma migrate reset`（治标）。

**机制（这次查清了）**：`cleanState()` 在开场发现「上一轮把人留在岗」时会补一次下班，
而**同一张合成照片**在短时间内连拍两次会被判 `SUSPECT_REUSE` ——
**这一条本身就是新的待处置异常**，于是队列变成 2；而该 spec 的多处断言写死了
`= 1` / `= 0` / 「队列整个空了」，等于**隐含依赖『库里没有别人的条目』**。

**三处修法**（保留原意，去掉隐含依赖）：
1. **除根**：`cleanState()` 补完下班后，把它**自己造出来的那条**顺手处置掉
   （spec 尾部本来就是这么给自己收尾的）。
2. **相对量**：`pendingBefore` / `itemsBefore` 开场取基线，断言「比之前多 1 / 少 1」——
   队列本来就是**工作队列**，带着别的条目是正常的。
3. **精确到那一条**：把「队列整个空了」（`attendance-queue-empty`）换成
   「**被处置的那一条**不在队列里了」（`review-item-<id>` 计数 0）——
   仍然证明「处置会把它从队列里拿掉」，但不再要求库里没有别的异常。

## 影响

- 侧边栏品牌区显示店名（多租户下这才是「我在哪」）。
- e2e 从「跑一次就必须 reset 一次」变成**可以连着跑**：实测不重置连跑 **3 次全绿**（55/55/55）。
- 没有触碰任何数据分区逻辑（`branch-scope.ts` 一行未动）—— P5 最危险的那部分留给单独一片。

**没有做变异测试**：这次改的是 UI 文案 + e2e 断言，没有新增「守卫」类逻辑；
用**连跑三次不重置**替代了它 —— 那正是这个 bug 原本的复现条件。

**方法论**：`python3 - <<'PY'` 里用 ASCII 双引号写中文注释 → SyntaxError（今天第三次），
后来改用 edit 工具。**批量改文件不要用 Python 写中文。**

### P5 剩下的

- **`branch-scope.ts` 隔离职责退役**（90 处调用，涉及数据分区 —— 单独一片，先摸清每处的语义）；
- `?branch=` 残留 3 处（`workshop/bookings` 的 searchParams 声明、`rider/book`、`qr/workshop`）；
- `branch-info.ts` 只剩 seed 在用 —— 可以顺手降级成「演示数据常量」并加注释说明。
