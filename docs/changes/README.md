# docs/changes — 一次改动一个文件

## 为什么改成这样

以前每次改动都往 `docs/SETUP_AND_PREPARATION.md` 的 §9 台账**顶部**插一行、往 `docs/HANDOFF.md` **顶部**插一段。
只要同时开着两条分支，第二条合并时**必然冲突**——两边改的是同一批行。这个冲突到目前为止已经发生了两次，
每次的解法都是「取 main 的版本、再把自己的条目按锚点插回去」，纯属重复劳动，而且手工合并文档本身就有抄错的风险。

**根因不是大家不小心，是结构问题**：一份共享文件里的同一处位置，天然只能容纳一条分支的改动。

## 现在的规矩

1. **新改动：新建一个文件** `docs/changes/YYYY-MM-DD-<简短英文名>.md`。
   两条分支各自新建**不同文件**，git 永远不会冲突——这是这个约定存在的唯一理由。
   跑 `pnpm new:change <名字>` 会自动生成骨架。
2. **不要再往 §9 台账加行，也不要再往 HANDOFF 顶部加段落。** 那两处已**冻结**，作为历史保留。
   有测试（`tests/docs-changes.test.ts`）盯着这条：一旦有人往冻结区新增条目就会失败，并告诉他该往哪写。
3. 改动说明写在文件里，不写在共享文件里。

## 文件格式

```md
---
date: 2026-09-11
title: 一句话说清改了什么
branch: fix/example-branch
---

## 改动

（具体做了什么）

## 影响

（对使用者/系统意味着什么）

## 交接说明

（为什么这么做、踩了什么坑、下一会话需要知道什么）
```

## 和 HANDOFF 的关系

`docs/HANDOFF.md` 负责**稳定的**东西：怎么恢复服务、基线、约定、当前未完成的事。
`docs/changes/` 负责**逐次改动**的记录。续接会话时：读 HANDOFF → 再按文件名倒序读最新的几个 change 文件。
