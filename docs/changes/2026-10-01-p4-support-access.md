## 改动

P4 第三块的第二半，也是这一块里**安全上最讲究**的一件。

问题：平台人员"看租户数据"这个能力是必要的（店里出问题不能靠猜），但它的危险不在"看"，
而在**看是不可见的**。所以这条路径上的每一环都要能解释。

1. **`SupportGrant` 表**（限时授权）：`organisationId` / `grantedByAuthId` / `grantedByEmail` /
   `reason`（**必填**）/ `expiresAt` / `revokedAt` / `createdAt`。**不挂外键** —— 与
   `PlatformAuditLog` 同理：退租删掉整家店之后，"谁在什么时候被允许看过它"必须还在。
2. **四条约束**（服务层，不靠 UI）：
   - **限时**：时长必须落在 **5–480 分钟**；`expiresAt` 每次渲染都重新判（显式 `now` 可测）。
   - **必须写原因**（≥4 字）：审计的第一性问题。
   - **按人授权**：授权写清是哪个平台管理员，**只有他能用** ——
     "谁都能用别人的授权"就没有留痕的意义。
   - **随时可撤销**：`revokedAt` 一填立刻失效。
3. **双向留痕**：每一次授予 / 查看 / 撤销都写**两条**——
   平台侧 `PlatformAuditLog`（`SUPPORT_GRANTED` / `SUPPORT_VIEWED` / `SUPPORT_REVOKED`）
   **和租户自己的 `AuditLog`**（`SUPPORT_ACCESS_*`）。后者直接出现在租户的
   `/workshop/settings/audit-logs` 里（那个页面本来就有，不需要新 UI）——
   **租户看得见平台来过**，这才是"双向"。
4. **`/platform/<slug>/support` 支持会话页**：
   - 没授权时只有授权表单（**租户数据一个字段都不展示**）；
   - 有授权时展示**白名单式只读快照**（计数 / 最近 10 条工单 / 员工 / 租户自己的审计），
     外加"立刻结束会话"。
   - **先记后读**：本次查看的审计行在读审计列表**之前**写入，所以"我这次访问"就在列表里 ——
     否则看的人会以为没记上（审计页的第一要求是可信，不是好看）。
5. **测试 +12**（`tests/platform-support-access.test.ts`）。

## 影响

- 平台侧有了一条**正当**路径去看租户数据：限时、有原因、按人、可撤销、**双方可见**。
- 租户在**自己的**审计日志里能看到平台何时被允许进入、何时查看、何时撤销 ——
  不需要信任平台的单方面说法。
- 支持会话是**只读**的：那个目录里没有任何 server action、也没有写库（有结构守卫盯着）。

**实测证据**：

|---|---|
| `tsc --noEmit` | 0 错误 |
| `pnpm test` | **1072 通过 / 95 文件**（1060 + 12） |
| `pnpm lint` | 退出码 0（830 warning / 0 error） |

| Playwright | **55 通过**（第一次跑红了 2 条考勤用例，见下） |
| UI 全流程（一次性租户） | 初始只有授权表单 → 授权后「支持会话进行中」+ 只读快照 + 原因入审计 → 立刻结束 → 回到表单 + 历史里有撤销；**零控制台错误** |
| DB 双向留痕 | 平台侧 `SUPPORT_GRANTED×2 / SUPPORT_VIEWED×2 / SUPPORT_REVOKED×2`；租户侧 `SUPPORT_ACCESS_GRANTED×1 / VIEWED×1 / REVOKED×1`；授权行带原因与 `revokedAt` |

**变异测试（四条约束，都实测会红）**：
- 授权忽略"按人"（`findActiveSupportGrant` 不看 authId）→ 红 1 条（"别人的授权也能用"）。
- 不判过期（去掉 `expiresAt > now`）→ 红 1 条（"过期了还能用 = 限时是假的"）。
- 查看只写平台侧（去掉租户侧那条）→ 红 1 条（双向留痕）。
- 支持页里加一句写库 → 红 1 条（结构守卫点名"支持页不该直接写库"）。

**一次"看起来像我改坏了"的 e2e 红（查清了才敢说无关）**：第一次跑 e2e 时
`e2e/attendance-review.spec.ts` 红了 2 条（`待处置` 期望 1 实际 2）。没有想当然归因于"考勤与我无关"，
而是去 `e2e.db` 里看了 punch 轨迹：本轮的 3 条 punch 是
`IN OK (02:36:14)` → `OUT SUSPECT_REUSE (02:36:18)` → `IN NO_LOCATION (02:36:23)` ——
即 spec 的 `cleanState()` 补了一次下班，而**同一个合成摄像头**连拍两张被判定为"复用照片"，
于是队列里多了一条。根因是 **e2e 库跨运行累积了状态**（这个 spec 依赖"没有未收尾的在岗"）。
`DATABASE_URL="file:./e2e.db" pnpm exec prisma migrate reset --force`（含 seed）+ 重启 e2e 服务后
**55 全绿**。教训：e2e 红先看**数据库里的实际轨迹**再下结论 —— 既不能"因为不是我改的模块"就忽略，
也不能急着改代码。

**踩到并顺着修掉的一处 UX/信任问题**：第一版 UI 冒烟里"平台侧三条留痕"是 false ——
不是没记（DB 里有），而是页面在**读审计之后**才写"本次查看"，于是自己这次访问不在列表里。
改成**先记后读**之后同一屏就能看到 `SUPPORT_GRANTED` + `SUPPORT_VIEWED`。
审计页最怕的不是丑，是"看起来没记上"。
