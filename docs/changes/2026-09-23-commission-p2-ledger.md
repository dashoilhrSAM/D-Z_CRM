## 这一期做什么

P1 让「该给多少钱」有了唯一答案；P2 让这个答案**真正落账、可审计、不会重复给**。

1. **CommissionLedger 台账（只追加）** —— @@unique([jobItemId, kind]) 是幂等的**数据库层**保证：
   完工流程被重跑（双击/重试/补偿任务）时第二条根本插不进去。改错只能追加 ADJUSTMENT/REVERSAL，
   永不 UPDATE 原值 —— 否则「上月他到底拿了多少」就再也说不清（历史工资单与银行流水会对不上）。
   规则内容以 ruleSnapshot 快照保存，事后改规则不影响历史（与促销「报价即承诺」同一套原则）。
   jobItemId 可空（调整行没有对应工单行），而 SQL 的唯一索引把 NULL 视为互不相同 —— 有意利用。

2. **计提引擎** src/modules/commission/engine.ts —— **唯一写入者**，在完工事务内调用：
   活干完、账单、佣金三者要么一起成立要么都不成立，不存在「活干完了但佣金没计」的中间态。

3. **佣金基数＝客户实付**：把发票折扣（促销 + 柜台手工）按行占比分摊，尾差归最大行、
   单行承担额不超过它自己的金额（净额永不为负）。老板若要按原价算，用
   Organisation.commissionOnGross（默认 false，页面可开关，不写死源码常量）。

4. **没指派技师不许静默算 0**：写 kind=PENDING 的台账行（金额 0 + 原因），进「待归属」清单；
   补指派后重跑本函数会补上正式 BASE 行。**免费行/保修行（unitPriceSen=0）与拒单行完全不参与**
   （不计佣也不计件）。没有任何规则覆盖的行留一条金额 0 的 LEGACY 痕迹（钱仍由旧的人员级结算付，
   所以是 0 而不是猜一个数），并出现在对账报告的「未覆盖」清单里。

5. **「人工改佣金」改成写调整台账**：updateJobCommission 不再直接改数字，而是追加一条 ADJUSTMENT
   （带原因与操作人）再把显示用汇总字段回填为台账合计。ServiceJob.commissionSen 从此**只是汇总**。

6. **对账报告** scripts/commission/reconcile.ts —— 设计稿 §4.5 的三条不变量：每行恰好一条 BASE、
   佣金 ≤ 该窗口发票收入、台账 vs 结算（差额先呈现不判红，P4 才切）。硬不变量被破坏时 exit 1，
   可以挂进定时任务。报告**区分历史工单与配置缺口**：P2 之前完工的单子本来就没有台账
   （设计稿明确历史不重算），混在一起报会天天红着说「17 行有问题」，真正的缺口反而被淹没。

## 验证

- 新增 **22 条测试**（口径纯函数 13 + 计提 5 + 源码护栏 4），全量 **53 文件 / 669 测试通过**，tsc 干净。
- 计提测试跑在真库上（幂等只能这样验证）：折扣后净额 8100 × 5% = **405**；
  **第二次调用 based=0 / skipped>0，台账行数不变**；免费行不留任何行；无发票不计提；
  无技师写 PENDING 而不是静默 0。
- 源码护栏把「只能有一个写入者」变成会失败的测试：src 下没有任何 commissionLedger.update/delete；
  写 commissionSen 的地方**只有** settlements 一处，且那一处必须同时写 ADJUSTMENT。
- 对账脚本在 dev.db 真实跑通（exit 0，历史工单 17 行被正确归类为「历史、有意不回填」）。

## 尚未做（有意留在后面）

- **零件行不计佣**：本期只对 ServiceJobItem 计提。零件是另一张表（ServiceJobPart）且没有目录身份，
  而「技师要不要按零件额提成」是个业务问题——需要老板定，定之前不猜。
- 历史工单不重算（设计稿口径）；阶梯奖励（P3）；台账→结算整合与期间锁（P4）。
- 完工流程的端到端断言（经 completionService.complete 走一遍）还没写：引擎本身有测试，
  接线是一行、在既有事务里，但这不等于验证过——补一个 e2e 比自认为安全划算。
