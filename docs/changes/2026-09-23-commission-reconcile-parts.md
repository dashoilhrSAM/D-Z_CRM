## 为什么要补

对账的「每条计费行都有归属」这条不变量（设计稿 §4.5 第 2 条）**只看服务行**：
它遍历的是 ServiceJobItem，从来没看过 ServiceJobPart。

零件计佣刚上线（PR #60）—— 也就是说，**那道「最后一道网」上正好有一个洞，位置就在新功能上**：
一条有价格的零件行如果因为任何原因没写台账，报告不会吭声。

## 怎么补（以及为什么必须尊重那个开关）

- 给工单查询加上 parts 与 job.branch.organisationId；台账行按 jobPartId 建索引；
- 零件行与服务行**同一套判定**：多条 BASE → 硬错误；PENDING → 待归属清单；一条 BASE 都没有 → 未覆盖清单；
- **只在零件计佣开关打开的组织里检查** —— 关掉的组织零件本来就不该有台账，报它就是误报，
  而误报会让真报告失效（这条原则在本文件里已经用过两次：历史工单、已付款工资单）。
- CLI 输出也加上了零件统计。

## 写测试时踩到的一个坑（值得记）

第一版测试挂了，billablePartLines 拿到 0。原因不是代码：
这个测试文件顶部的夹具里，台账行是为「结算对比」写的、**没有 jobId**；
而覆盖检查只处理「台账里出现过的工单」（没有台账的算历史工单，按设计不重算）。
于是那几张工单全都走了 continue，我新加的零件**根本没进入检查**。

教训：**当一段逻辑刻意跳过某一类数据时，测试必须把数据造在「被检查的那一类」里** ——
否则测试会因为错误的原因通过或失败（这次是失败，反而算运气好；如果它碰巧断言成 0 就该红了却说不出原因）。

改法是另造一张**自带台账行**的独立工单，零件放在它上面；顺带给夹具的 ledgerRow 加了可选的 jobId 参数，
并在注释里写明两者的用途不同（结算对比 vs 覆盖检查）。

## 验证

- 该文件 **9 条测试**（新增 2 条）：开关开时无台账的零件行进入未覆盖清单、开关关时完全不检查且不产生硬错误；
- 全量 **60 文件 / 735 测试**通过，tsc 与 eslint 干净。
