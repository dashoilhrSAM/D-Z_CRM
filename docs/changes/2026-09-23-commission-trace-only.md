## 怎么发现的（不是测试发现的，是**准备生产实跑**时推出来的）

老板要我「让引擎在生产上跑一单」。准备时我先查了一件事：生产里的佣金规则有几条？
答案是 **0 条**（CommissionRule 全空）。

于是推下去：这一单完工后，每一行都会解析不到规则 → 按设计写入 **LEGACY 行**（金额 0，
reason = 没有被规则覆盖，钱仍由旧的人员级结算付）。

再看我的 P4 判定：resolvePayoutCommission 用的是「**有没有台账行**」——
而 LEGACY 行**也是行**。于是 rowCount > 0 → 引擎认为「台账里有数」→ 用台账总额（0）
覆盖结算的佣金 → **把技师这个月的佣金清零**。

而 LEGACY 的语义恰恰相反：设计稿写的是「钱仍由旧的人员级结算路径付」。
换句话说：**没配规则时跑一单，会把技师的工资抹掉**。

## 改法

1. LedgerKindSum 新增 amountRowCount（**带金额**的行数：BASE / TIER_BONUS / ADJUSTMENT / REVERSAL），
   与 rowCount（含 0 元痕迹）分开；
2. resolvePayoutCommission 的判定改用 amountRowCount：只要**没有一行带金额**，就保留旧口径；
3. 提示语区分两种情形：完全没行 / 有行但都没钱（后者更值得警惕，正是「没配规则」的信号）。

## 验证

- 新增回归测试：「只有 0 元痕迹（没配规则）→ 必须保留旧口径」；
- 全量测试通过，tsc 与 eslint 干净。

## 这一轮的意义

这个 bug **今天就会在生产上发生**（规则 0 条 + 走一单 = 清零），而且它是沿着
「我要真的跑一遍」这条线才浮出来的 —— 单测当时只覆盖了「一行都没有」的情形。
**准备真实操作，本身就是一次最有效的测试。**
