## 为什么补这个

P2 合并时我明确写了三个"没做"的，其中一个是：**完工路径的端到端断言**。理由是——

> 引擎自己有测试、接线只有一行、且那一行在既有事务里，但这三件事加起来**不等于验证过**。

真实风险是"接线对了但**顺序**错了"：比如发票还没建就计提，于是基数拿不到（佣金会静默变成 0）。
这种错在单测里完全看不见，只有真的跑一次 CompletionService.complete 才会暴露。

## 这条测试断言什么

走**真实完工流程**（开票、付款、库存、忠诚度、服务历史、提醒、完成通知全部照跑），只断言与佣金有关的部分：

1. 发票建立且工单变 COMPLETED；台账里**有且只有一条** BASE（免费行不产生任何行）；
   金额 = 9000 × 5% = **450**，且台账行的 invoiceId 确实指向这张发票（证明基数来自发票而不是别处）；
2. 返回结构里的 commissionAccruedSen 与台账一致；
3. **再完工一次**（幂等路径）：不产生第二条台账，返回的金额**读自台账**而不是重算；
4. 没指派技师的工单：写 PENDING（金额 0 + 原因），不静默算 0。

## 写这条测试时踩到的两个坑（都会让测试变成"长期污染源"）

1. **清理漏表 → 删客户撞外键**：完工流程会写 Review / Notification / **Message**（完成通知真的落库），
   它们都挂在 customerId 上。少了任何一个，afterAll 都会在删客户时报外键错误 ——
   而 vitest 仍然显示"3 passed"，于是错误只在日志里滚过去。**测试通过 ≠ 测试干净**。
2. **车牌用时间戳前 6 位不唯一**：base36 时间戳的前 6 位几小时内都不变，于是几分钟后的下一次运行
   撞上残留车牌（Unique constraint failed on plate）。改成取尾段 + 随机后缀。

两个坑的后果都是"下一次运行莫名其妙地失败/污染 dev.db"。已清掉此前遗留的 7 个测试组织。

## 验证

- 新测试 3 条全过，且**清理不再产生任何 Prisma 报错**；
- 全量 **54 文件 / 672 测试**（669 通过 + 3 skipped）；tsc 干净。
