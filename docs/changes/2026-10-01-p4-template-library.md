## 改动

P4 第三块的最后一件。

开第一家店时默认配置"差不多就行"；开到第五家时，你会希望把**已经调好的那家**复制过去。
所以"新店长什么样"不该是散在服务里的常量。

### 1. 两条来源，解析顺序**自定义 → 内置**

| 来源 | 位置 | 为什么需要它 |
|---|---|---|
| **内置** | `src/modules/platform/templates.ts` 的 `BUILTIN_TEMPLATES`（`standard` / `dealer-only`） | 永远存在、可复现 —— 新装一套系统也能开出门店 |
| **自定义** | `TenantTemplate` 表（**从某家店导出**的） | 连锁开店最省事的一条路 |

**刻意不把内置也塞进库**：那样会有两份事实来源（改了代码而库里是旧的），
本项目在别处吃过这个亏（`role-modules.ts` 的"影子副本"）。

**列表顺序与解析顺序必须一致**（自定义在前）——否则"列表里看到的"和"开新店用到的"
不是同一个，而这种错**不会报错**。

### 2. 模板是不可信输入

负载可能来自"某家店导出的 JSON"，所以用 zod 校验形状（服务目录 / 线索来源 / 线索阶段 /
消息模板，各有条数与字段上限）。**坏形状返回 null 而不是抛**：一条坏模板不该让列表页 500，
列表里跳过它、开新店时明确拒绝。

**找不到模板 → 拒绝开通**（`TEMPLATE_NOT_FOUND`），**不静默退回默认配置** ——
"我明明选了模板"变成一句空话是最难查的一类问题。

### 3. 导出只搬配置，不搬业务数据

`saveTemplateFromTenant` 读的是这家店**当前**的服务目录/线索来源/线索阶段/消息模板
（`active` 的），不碰客户、工单、发票 —— **模板不是备份**。导出会留平台审计
（`TEMPLATE_SAVED`，记清是从哪家店导的）。空配置的店会被拒绝导出（导出来也没用）。

### 4. UI

- `/platform/templates`：列表（自定义在前，标注来源与四类计数）+ 从某家店导出 + 删除自定义。
- `/platform/new`：开通表单顶部有**模板选择**，选项里带计数（"会建出多少东西"）。

### 5. 测试 +12（`tests/platform-templates.test.ts`）

其中最关键的一条是**遮蔽内置**：保存一个 key 撞内置（`standard`）的自定义模板，
然后开新店必须拿到**自定义那份**配置。少了它，"自定义优先"这条规则**没有任何测试能观察到**
（因为自定义 key 与内置不冲突时，两种解析顺序结果相同）—— 这是变异测试逼出来的。

## 影响

- 开新店可以选择套哪套配置；连锁店可以把调好的那家一键变成模板。
- 内置模板也走同一道形状校验（内置也是数据）。
- 老的默认配置行为**完全不变**：不指定模板时就是 `standard`，内容与之前散在服务里的常量逐条一致。

**变异测试**：
- 解析改成"内置优先" → **先是不红**（说明测试没观察到这条规则），补了"遮蔽内置"断言之后 → 红 1 条 ✅
- 模板找不到就静默退回默认 → 红 1 条 ✅
- 列表顺序反过来 → 红 2 条 ✅

**顺带被守卫抓到一次**：新增模型 `TenantTemplate` 之后，
`tests/platform-tenant-purge.test.ts` 的**"生成器可复现"**断言红了 ——
生成文件确实过期了（`NON_TENANT_MODELS` 少一项）。重新生成即可，`PURGE_ORDER` 81 项不变。
这正是那条断言存在的意义：新增模型会主动提醒你"退租计划需要重新核对"。
