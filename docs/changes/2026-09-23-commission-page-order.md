## 老板的原话

1. 「分类好每一个 function，现在 reward target and all rules 太下面，花很久才看到，可以一到 simulator 下面」
2. 「simulator 细节一点，有点看不懂」

## 一、顺序：先给「现在是什么样」，再给「改哪里」

改前：标题 → 开关 → 成本卡 → 【试算器 → 搜索 → 82 项逐项清单 → 全部规则】→ 奖励目标（页面最底）。
两个总结性的东西（奖励目标、全部规则）被压在一张长清单的两端，老板要滚很久。

改后：

  ① 怎么算（业务开关 + 本月成本）
  ② 先算一遍（试算器）
  ③ 奖励目标（从页面最底上移）
  ④ 全部规则（从逐项清单之后上移）
  ⑤ 逐项设置（82 个 SKU 那张长清单，放最后）

**最长的那张清单放最后**是有意的：它代表工作量，不是每次打开页面都要看的东西；
而「我配了什么规则」「奖励目标是什么」是每次都想先看到的。

## 二、试算器：从「一行字」改成「讲得清」

改前：三个没有标签的输入框（只有 placeholder）+ 一行结果「RM 9.00 matched DEFAULT rule (5%)」。
老板看不懂的是**这个数字怎么来的** —— 所以现在给四样东西：

1. **输入有标签**：卖的是什么 / 这一项收了多少钱 / 数量；并写明「只看数，不写入任何东西」。
2. **算式**：按比例 → 「RM180.00 × 5% = RM9.00」；按件 → 「RM2.00 × 3 = RM6.00」；组合 → 两者相加。
3. **命中的是哪一层**（SKU / 服务 / 套餐 / 分类 / 默认）。
4. **五层解析表**：逐层显示「这一层有没有规则、会算多少」，并高亮**实际用的是哪一层**；
   底下写清楚「某一层没配就往下找，全都没有才按旧口径」—— 所以「没配」不等于 0，它是继承。

改后完全没有规则的后果也写明白了：按旧的人员级结算发放，台账留一条 0 元痕迹（不静默算 0、也不猜一个数）。

## 三、一个刻意的技术约束

试算结果（含五层解析）**全部由服务端算**，用的是与发薪同一个解析器；界面只负责显示。
界面自己再算一遍 = 两个实现，迟早会与发薪漂移 —— 这种「页面上算出来的和实际发的不一样」，
是这类系统里最难被发现的错误之一。为了显示算式，服务端把规则本身的结构（basis / value /
valuePercent / valueFixedSen）也一并返回，界面不做字符串抠数字。

## 验证

- tsc 与 eslint 干净；全量测试通过（另有一次偶发失败已单独建档跟踪，与本改动无关）；
- 新增 20 条三语文案（试算器说明 + 五个分区标题）。

## 没做的事（避免越改越多）

没有给页面加编号徽章、没有重排每个卡片内部的字段 —— 老板要的是「看得见」与「看得懂」，
不是视觉翻新；已有卡片自带的标题（How commission is calculated / Reward targets / All rules）继续沿用，
避免同一件事出现两个标题。
