## 改动

新增 scripts/perf/load-mix.mjs：本机没有 k6，用 Node + Playwright 自建并发 harness。
登录一次拿会话 → 按容量报告的浏览配比（自动刷新 67% + 各列表页 11%）逐步加并发 →
输出 req/s、p50/p95/p99、错误数、3xx 数、以及**服务端 CPU 核数**（Vercel Fluid 的计费单位）。
配比可用 MIX 环境变量覆盖，这正是做「去掉某个嫌疑路由」对照实验的开关。

只打只读浏览，**不含上传与写入**：这一轮打在 perf.db 上，写入会污染造好的量数据，
而且写并发（锁/事务）是另一类问题，要单独一轮。

## 影响：找到了比「缺缓存」严重得多的问题

同一实例、同一份代码，单并发与四并发对照（Mac17,9 / 15 核 / 本机 SQLite）：

| 路由 | 并发 1 | 并发 4 | 判读 |
| --- | --- | --- | --- |
| /workshop/dashboard | 145 req/s，p50 7ms | 197 req/s，p50 20ms | 健康 |
| /workshop/bookings（4,338 行） | 150 req/s，p50 6ms | 221 req/s，p50 18ms | 健康 |
| **/workshop/jobs**（7,308 行） | 9.9 req/s，p50 100ms | **2.3 req/s，p50 1959ms** | **并发越多越慢** |
| **/workshop/customers**（4,202 行） | 3.1 req/s，p50 323ms | **1.23 req/s，p50 3631ms** | **并发越多越慢** |

**机制（实测，不是推测）**：这两个页面把整张表连同深层关联一次拉出来，每个请求要构造
巨大的对象图，随即丢掉 99%。顺序请求时 /workshop/customers 是 0.35 CPU 秒；
**四并发时同样的四次请求花了 14.15 CPU 秒 = 每个 3.5 CPU 秒，放大 10 倍**，
RSS 一次 +223MB（实例基线已 1.4GB）。这是 GC/内存压力，不是数据库慢。
dashboard 在那次风暴之后单独打一次仍要 11ms（空闲 7ms）——实例是被**排队**拖住的。

**后果**：把 /workshop/customers 放回配比，整轮吞吐从 23.3 req/s 掉到 10.5 req/s、
每请求从 640 核·毫秒涨到 1626 核·毫秒。也就是说**少数几个人打开这一页，会让同一实例上
所有人变慢**（生产上共用一个 Fluid 实例的正是同一家门店的柜台与机修）。

顺带纠正一个我自己的说法：bookings 的 list() 同样没有 take/where（4,338 行），但它健康。
所以真正的判别标准不是「有没有 LIMIT」，而是**每个请求构造的对象图有多大** ——
关联越深，并发下的放大越猛。

## 交接说明

- 全程**零错误、零 3xx**：这个问题的表现是「慢」，不是 500。生产上它不会被报错抓到，
  只会被体感抓到——这解释了为什么它一直没被发现。
- **不要把上表的绝对 req/s 当成 Vercel 容量结论**：本机单进程 + SQLite，且压测器与
  被测服务抢同一台机器的 15 个核。能跨环境迁移的是**形状**：无界取数 + 深关联 + 并发
  = 代价超线性增长。
- 下一步（按证据排序）：① 给 /workshop/customers 与 /workshop/jobs 的列表取数加
  where/take，把分页与搜索下推到 DB，聚合只算当前页的 id；② 再跑一遍这个 harness 做
  前后对照（同一 MIX、同一起点）；③ 参考数据缓存仍排在后面 —— 热点里没有它。
- 用法：DATABASE_URL="file:./perf.db" next start -p 3210 & 然后
  APP=... SERVER_PID=$(lsof -ti :3210) PASSWORD=... STEPS=5,15,30 node scripts/perf/load-mix.mjs
  （**别打 :3002/:3003/:3102，更别打生产**。）
