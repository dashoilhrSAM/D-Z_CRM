## 改动

P1 把打卡记成了不可变证据链，但看板只有「今天」，而且异常只是行尾一个**没人能清掉**的数字。
这轮把这两件事补齐，并刻意**不动任何原始记录**。

- **区间报表**：新增区间解析（今天 / 本周 / 本月 / 自定义），走 URL（`?preset=&from=&to=`）而不是组件内状态——
  报表要能被分享、刷新不该跳回今天。四个 KPI：出勤人天 / 总工时 / 记录异常 / 待处置。
- **CSV 导出** `/api/attendance/export`：按人按天的明细（员工/角色/分行/日期/上班/下班/工时/异常/待处置），
  给财务算工资用。时间**显式按组织时区**用 `Intl.DateTimeFormat` 渲染——服务器时区在本地(+8)与 Vercel(UTC)
  差 8 小时，同一份工资表在两处跑出不同的上班时间是不能接受的。
- **异常处置（新表 `AttendanceReview`，只追加）**：有 `ATTENDANCE:edit` 的人对每一笔异常判「成立 / 不成立」，
  可带备注；结果留痕（`ATTENDANCE_REVIEW_CONFIRMED|DISMISSED` 审计），弹窗与证据条上都能看到是谁、什么时候判的。
- **纯函数两层**（`range.ts` / `ledger.ts`，无 DB、无网络）：日期算术与「多天多人压成一张表」是唯二
  「算错了也看不出来」的部分——界面照样显示一个日期、一个数字。抽出来才能在单测里把跨天、未闭合、
  处置状态这些组合逐个钉死（新增 18 例）。
- **列出作用域内的所有人**（含区间内一条记录都没有的）：报表第一个要回答的问题往往是「这周谁没来」，
  不出现的人答不了这个问题。停用但有记录的人也显示（否则数据对不上）。

### 两条不会让步的口径

1. **处置不改任何原始行**。`AttendancePunch` 不更新，`Attendance.exceptionCount` 也不重算——
   那个数字回答的是「系统当时判了几笔异常」。处置是「人对这个判定的看法」，另存一张只追加的表；
   改主意就再追加一条，最新的算数。界面同时显示「记录到的异常」与「还没处置的」。
2. **队列是全时段的工作队列，不跟着报表区间走**。老板默认看「今天」，若队列也只看今天，
   上周留下的异常就**永远没人看见**——这正是本项目栽过一次的「功能在但没人找得到」
   （见 `docs/changes/2026-09-15-attendance-evidence-punch.md` 的权限矩阵那条）。所以：
   队列与「待处置」KPI 都是**全时段**的，不在所选区间内的项会被明确标出「区间外 · <日期>」。
   KPI 上的数字**永远等于队列的行数**，老板可以数着核对。

## 影响

- **对老板**：能回答「上月谁来了多少天、干了多久」「这周谁没来」，能导出给财务，
  并且异常有了处置入口——不再是看板上一个清不掉的数字。
- **对主管**：`ATTENDANCE:edit`（OWNER / MANAGER / SALES_MANAGER / SERVICE_MANAGER）才能判；
  柜台与销售只有 `:view`，看得见队列但没有按钮（e2e 里按非通配角色实测）。
- **对员工**：什么都不变。原始打卡记录、当日汇总、照片与定位的可见范围都没动。
- **数据库**：新增 1 表 + 1 外键 + 3 索引，两条迁移 `20260917021000_add_attendance_review` /
  `20260917023000_attendance_review_punch_fk`（sqlite，**纯加性**；第二条是给新表补外键，
  SQLite 不支持给已有表加 FK，按 Prisma 标准做法重建该表——表在本分支刚建、数据为空，重建零风险）。
- **生产**：由构建期 `scripts/sync-prod-schema.mjs` 自动建表加外键。
  已用只读检查实测过将要应用的 SQL（`DRIFT_CHECK_URL="$DST_DATABASE_URL" node scripts/sync-prod-schema.mjs --check`）：
  **1 表 + 3 索引 + 1 外键，零 DROP/TRUNCATE**。
  ⚠️ **合并前请先合 `fix/schema-drift-fails-the-build`**：那条护栏是「生产无法验证 schema 就拦住构建」，
  本次是它上线后的第一个 schema 变更。

## 交接说明

### 一条被刻意保留的不对称

`AttendanceReview.punchId` 加了 relation（外键 + `AttendancePunch.reviews`），
`AttendanceCorrection.punchId` **没有**。原因是查询需要：队列的定义是「哪些异常还没人处置」，
有 relation 才能用 `reviews: { none: {} }` 在数据库里一次问出来（count 与分页两个查询都走索引）；
只存字符串就得把全部 punchId 拉回内存再 `notIn`，区间一大就退化成全表扫描。
`AttendanceCorrection` 至今零调用，等真做「更正审批」时再定它的形状——**不要为了对称而改它**。

### 几个刻意的取舍

- **导出用路由而不是 Server Action**：下载要的是浏览器原生文件下载，走 fetch + Blob 反而要在客户端
  再拼一遍字符串，两处格式必然漂移。CSV 输出带 UTF-8 BOM（Excel 直接打开中文名不乱码）。
- **「还没有下班卡」分两种**：只有**今天**未闭合才显示「在班」，历史那天显示「未打下班卡」。
  混为一谈会让老板以为人两天没回家。（这是本地实走时发现的，见下。）
- **未闭合的那一段不计工时**（沿用 P1 的 `rollupDay`）：所以历史某天忘打下班卡时，
  那天工时是 0 而不是「从上班到现在」——这是有意的，不是 bug。
- **自己也能判自己的异常**：不做「不能自审」的限制，否则店里只有一个人有权限时会走进死胡同；
  但审计里记着是谁判的、可追溯。

### 踩到的坑

- **「在班」文案对历史记录是错的**：第一版本地对账时看到 9/15 那笔未闭合的 IN 也被标成 ON DUTY。
  夹具本身没问题（`rollupDay` 一直返回 INCOMPLETE），错的是**界面把「未闭合」直接当成「在班」**。
  修法是只有今天才显示「在班」，历史显示「未打下班卡」。
  **这条只有真的打开页面用一段跨越几天的时间看才会发现**，断言"页面上有 INCOMPLETE"是抓不到的。
- **给已有表加外键在 SQLite 上要重建表**：`prisma migrate diff` 生成的 RedefineTables 是
  CREATE new → INSERT…SELECT → DROP → RENAME。表是本分支刚建的、数据为空，所以零风险，
  但以后对**有数据**的表这么改要先把重建窗口想清楚。
- **套件变长暴露了一个既有竞态（顺手修了）**：第一次全量跑 55 例时 `promo-at-checkin` 挂在
  `helpers.ts:115`（找不到那一行 booking），而**单独跑通过、与该 spec 加两条考勤 spec 一起跑也通过**、
  把新 spec 排除掉再跑全量 51/51 通过、再跑一次全量 55/55 通过 —— 是一次竞态而不是功能坏了。
  根因在共享助手：`setPersona` 点完 Sign in 之后 **sleep 1500ms**，赌一次 Supabase auth 往返一定够快。
  输了以后**不在原地报错**，而是让后面每一条断言都跑在登录页上（症状就是「某个 testid 一个都找不到」，
  看起来像功能坏了）。已改成等 middleware 真正认的那个 cookie（`sb-*-auth-token`，见 `src/middleware.ts`）。
  **没有把"猜"当成结论**：四条不同组合的跑法就是为了把「我的改动造成的」与「偶发」分开。
- **本机路径含 `&`**：bash 里引用项目路径必须加引号。
