## 这一期做什么

「卖 10 送 2」这类阶梯的**判定引擎**。做法严格照设计稿 §3，其中三条是硬规矩：

1. **不存「当前件数」计数器** —— 件数一律从台账推导（窗口内该技师、该作用域、kind=BASE 的合格行）。
   计数器 + 定时清零是这类系统最经典的事故源：漏跑一次就算错，而且没人会发现。
   窗口天然切换让「重置」这件事**在架构上不存在**。
2. **达档归属必须确定性** —— 两单落在同一毫秒时也要有唯一答案：按 (earnedAt, id) 排序后，
   **跨过门槛的那一条台账行**就是触发者。测试里专门验证「输入顺序反转，结果不变」。
3. **奖励金额在这个函数里算清**，并允许把触发的那条台账行写进快照 —— 争议时靠它解释，
   而不是靠人去翻数据库猜。

## 新增的东西

- 三张表：**CommissionTierSet**（含 scope / windowKind / countUnit / rewardKind / retroactive）、
  **CommissionTier**（门槛 + 奖励值，同组内门槛唯一）、**CommissionClaim**（领取记录，
  @@unique([userId, tierId, windowKey]) 保证同一人同一档同一窗口只能领一次）。
- **台账加三列** productId / serviceTypeId / category：件数要按作用域统计，就必须知道「这一行是什么」。
  与 ruleSnapshot 同一个道理 —— **统计不回头 join 可能被改的工单行**（台账是既成事实）。
  计提引擎已在这三处（BASE / PENDING / LEGACY）都填上。
- 纯函数层 src/lib/commission/tiers.ts：作用域匹配、计件（件/行）、
  进度与达档（含触发者）、三种奖励形态、可领取清单。

## 三种奖励形态（界面上的选项必须条条算得清）

| 形态 | 含义 | 算式 |
| --- | --- | --- |
| ONE_OFF_FIXED | 达成时一次性给 | rewardValue |
| EXTRA_PER_UNIT_FIXED | 每件额外加（可追溯） | 追溯：单价 × 窗口全部件数；不追溯：单价 ×（件数 − 门槛） |
| FREE_UNIT_COMMISSION | 「送 N 件的佣金」 | N × 该窗口平均单件佣金 |

## 刻意没做的三件（都写清楚，不装作做完了）

1. **countFreeLines 字段没有加**：免费/保修行在台账里**根本没有行**（P2 定的是不计佣也不计件），
   所以「免费行计入件数」无法从单一真相推导 —— 要么伪造台账，要么引入第二个数据源。
   老板的决定 4 就是「不算」，所以这里把该决定**烧进口径**，而不是留一个做不到的开关。
2. **STEP_PERCENT（达标后后续件提高百分比）没做**：它本质是**计提时**的行为（要改变后续行的 BASE 比例），
   不是领取时的奖金，需要在引擎里按行推进阶梯状态 —— 是独立的一块，留作后续。
3. **PAY_CYCLE / ROLLING_30D 窗口没实现**：碰到这两种 windowKind 会**明确抛错**，
   而不是悄悄按自然月算。窗口口径错着算出来的统计，比没有统计更糟。
