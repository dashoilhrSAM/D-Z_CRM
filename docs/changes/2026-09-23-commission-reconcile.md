## 这一期做什么

设计稿 §4.5 要求把三条不变量做成**可定时跑的报告**，并且「一旦不成立 → 页面顶部横幅提示，
**不给『就这样付了』的机会**」。

P2 时这些判定只存在于一个 CLI 脚本里（script/commission/reconcile.ts）—— **只有跑它的人看得见**。
这一期把它抽成模块 src/modules/commission/reconcile.ts，**脚本与页面共用一份实现**：
同一条规则写两遍，迟早会出现「脚本说没事、页面说有事」。

## 三条不变量现在的判定

1. **台账 == 工资单**（P4 之后这条才真正成立）。取数口径**必须与结算一致**：按 earnedAt 落在周期内
   （迟到的计提落当前窗口），而不是按窗口键匹配 —— 后者会把「上月工单本月完工」这笔记漏，然后报一个**假红**。
   分三种结果：一致 ✅；**未付款**却对不上 → **判红**（这时候还能重算）；**已付款**却对不上 → 只提示
   （金额已冻结，只能在下一期做调整）—— 已付款的差额不改历史，这正是设计稿 §4.4 的意思。
2. **每条计费行有且只有一条 BASE**：历史工单（P2 之前完工、台账里一行都没有）与配置缺口**分开报**。
   混在一起会让报告天天红着说历史有问题 —— 那是狼来了，真正的缺口反而被淹没。
3. **每个窗口的佣金 ≤ 该窗口发票收入**：超过就判红（「佣金超过营业额」这种离谱错误必须拦住）。

## 页面横幅（这一期真正新增的可见部分）

结算页顶部在不变量不成立时显示红色横幅：「结算数据待复核 —— 佣金台账与工资单对不上。
在弄清楚之前出粮，会把错的数字写进工资单。」并列出前几条具体问题。

两个刻意的处理：
- 报表**绝不能把被它报告的页面搞挂** → 包 try/catch；
- **但也绝不静默**：检查本身失败时显示「对账检查本身失败了：…」，而不是装作一切正常 ——
  否则这个横幅就成了新的「看起来没事」。

## 全量测试抓出的一个真 bug（差点上线）

对账模块最初**查全库**（所有组织）。单跑这个测试文件没事，**和其他测试文件一起跑就红** ——
因为别的测试造的 2026-09 台账与发票也算进了同一个窗口。

这不是测试噪音，而是真缺陷：**结算页的横幅必须只看本组织**，否则在多个组织的库里，
别人对不上账会让你的页面显示红色警告 —— 而**假警报会让真警报失效**。
已给模块加 organisationId 过滤，页面传 session.orgId，脚本不传（CLI 看全量）。
