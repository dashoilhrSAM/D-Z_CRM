## 改动

工单侧那次已经把 dashboard 的取行问题修掉（boardSummary 走聚合），但同一页还有两处在读全表：

1. **生命周期分布**：原来把每一张在办工单、每一条在办预约**逐行**取回来（只 select status），
   再在 JS 里逐行调 resolveStep 归类。改成两条 groupBy（工单按状态、预约按状态）。归类本来
   就只取决于状态，所以是等价且便宜的写法。
   其中一条语义搬到了 SQL 里：原来对「已经挂到工单上的预约」是 continue 跳过（由工单那侧计），
   现在写成 where 的 jobId: null —— 不搬过去就会把它们重复计一次。
2. **重复客户率**：原来是 db.customer.findMany({ select: { jobs: { select: { id: true } } } })
   —— 把全组织**每一个客户连同其全部工单 id** 读回来，再数「有 ≥2 张工单的客户」。
   改成两次计数：总数一条 count；「有 ≥2 张工单的客户」一条分组计数（原始 SQL，只回一个数字）。
   这段刻意仍不看分店（与改前一致，重复率是组织级口径）。

## 影响

| /workshop/dashboard | 改前 | 改后 |
| --- | --- | --- |
| 并发 1 | 126.3 req/s，p50 8ms | **146.2 req/s，p50 7ms** |
| 并发 4 | 175.6 req/s，p50 20ms | **196.9 req/s，p50 22ms** |

**本地提升不大，要说清楚为什么**：本机 SQLite 就在同一台机器上，这两条查询本来也走索引，
所以省下的是「传输与构造对象图」的时间；真正的理由是**数据量**——重复率那段原来随客户总数
线性增长（4,202 个客户 × 各自工单），而 COUNT(*) 是常数。放到生产 PG（跨网络）差距会放大。

## 交接说明

- **顺带修掉一条我自己写的偶发失败**（这条比它看起来重要）：上一版的
  tests/job-board-bounded.test.ts 把「聚合计数」与「另一条 count」分两次读、且不加作用域，
  单独跑永远绿，但整套并行跑时**连跑 4 轮红 4 轮**（别的测试文件正在写同一个 dev.db，
  两次读之间数据就变了，报 expected 4 to be 6 这类）。现在整套夹具挂在一个**自建分店**下，
  计数断言全部落在自己造的那份数据上。这是本项目「夹具必须自足」那条的又一次实例。
- 新增一条断言：dashboard 的生命周期桶必须与夹具的状态分布一致（2 张 WAITING → checked_in、
  1 张 READY → ready、5 张 COMPLETED 不计入，桶总数 3）—— 这条直接盯着「分组计数与逐行归类
  等价」这个改动本身。
- 基线：tsc 0 ／ vitest 874 → 875（76 文件，**连跑 3 轮全量全绿**证明偶发失败已消除）／ build 通过。
- 仍未做：混合负载（含全部路由）在并发 30 时的表现还没重测 —— 三个页面的曲线都修平了，
